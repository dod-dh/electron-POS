# 리테일 POS 데스크톱 클라이언트 v2

**Windows 매장 POS 앱 (Electron)** — 카드 단말기·백엔드 서버·로컬 DB 세 곳의 상태가 항상 일치해야 하고,
어느 한 곳이 끊겨도 **이중 승인·승인 누락이 생기면 안 되는** 제약 아래 설계한 실서비스 클라이언트입니다.

> 🔒 실제 운영 중인 상용 서비스이므로 **사명·서버 도메인·저장소 주소·VAN사 실명과 전문 규격·자격증명은 모두 제거**했고,
> 코드 조각은 원본 발췌가 아닌 구조 재작성입니다. 비공개 처리 내역은 [DESIGN.md §1](DESIGN.md#1-문서-범위와-공개-처리)에 항목별로 정리했습니다.

## 문제와 접근

POS는 일반 웹 서비스와 달리 **되돌릴 수 없는 부작용**을 다룹니다. 카드 승인은 수십 초가 걸리는 외부 단말기 통신이고,
승인은 됐는데 서버 확정이 실패하면 **고객 카드에서 돈은 빠져나갔지만 매출 기록이 없는** 상태가 됩니다.
반대로 재시도를 잘못 설계하면 **같은 카드에 두 번 승인**됩니다.

이 제약을 코드 규칙이 아니라 **구조**로 막는 것을 설계 목표로 삼았습니다.

```mermaid
flowchart LR
    UI["렌더러 (React)"] --> PL["preload<br/>채널 화이트리스트"]
    PL --> SVC["services (메인)"]
    SVC --> Q["결제 큐"]
    SVC --> API[("백엔드 API")]
    SVC --> DB[("로컬 SQLite")]
    Q -->|"Stage 1"| VAN[("카드 단말기")]
    Q -->|"Stage 2"| API
```

### 핵심 설계 판단 3가지

**1. 재시도 단위를 "결제 전체"가 아니라 "단계"로 쪼갰다**
카드 승인(Stage 1)이 성공하면 승인 결과를 큐 레코드에 먼저 기록하고, 서버 확정(Stage 2)이 실패하면 **확정만** 재시도합니다.
재시도가 카드에 두 번 닿지 않으면서 승인 기록도 유실되지 않습니다. 오류는 `retryable` 여부를 스스로 알려주게 만들어,
카드 거절처럼 재시도 가치가 없는 실패는 즉시 데드레터로 보냅니다.
→ [DESIGN.md §4.2 이중 승인을 막는 2단계 큐](DESIGN.md#42-이중-승인을-막는-2단계-큐)

**2. 카드 단말기를 8개 메서드 인터페이스 하나로 봉인했다**
VAN사마다 통신 방식이 전혀 다르지만, 서비스·큐·영수증 코드는 **어느 VAN사인지 모릅니다**. 매장 설정값 하나로 주입됩니다.
덕분에 신규 VAN사 추가가 파일 1개로 끝났고, "단말기 없는 무인 매장" 요구는 모든 동작이 no-op인 **가상 단말 프로바이더**가 그대로 흡수했습니다.
→ [DESIGN.md §5 VAN 추상화](DESIGN.md#5-van-추상화)

**3. 규칙을 문서가 아니라 런타임에서 막았다**
렌더러는 `ipcRenderer`에 접근할 수 없고, preload의 화이트리스트를 통과한 57개 채널만 메인으로 넘어갑니다.
채널 등록을 빠뜨리면 즉시 에러가 나므로 규칙이 강제됩니다. 같은 발상으로 **기본 환경은 항상 운영 서버**(개발 서버 선택은 별도 표식이 있는 PC에서만 노출),
**자동 업데이트는 서버 버전이 더 높을 때만** 실행해 롤백 시 전 매장이 구버전으로 되돌아가는 사고를 구조적으로 차단했습니다.
→ [DESIGN.md §3.2 보안 경계](DESIGN.md#32-보안-경계--preload-화이트리스트) · [§8 운영 안전장치](DESIGN.md#8-운영-안전장치)
